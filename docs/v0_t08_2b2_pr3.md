## 8. Atomicité

```
with db.begin_nested():                      # UN SAVEPOINT
    events._stage_certified_event(...)       # 1. INSERT événement (flush)
    db.add(attribution); db.flush()          # 2. INSERT attribution
    _mark_recorded(proof); db.flush()        # 3. UPDATE preuve -> recorded
```

(Depuis R1, l'ultime horloge est lue dans ce même SAVEPOINT, après le point 3 : § 8 bis.)

Ordre imposé par les FK non différables (attribution → événement, preuve → attribution). Le service ne fait
ni `commit()` ni `rollback()` ; `_stage_certified_event` refuse de s'exécuter hors du SAVEPOINT de
l'appelant et n'en ouvre aucun. Violation d'unicité (écrivain hors service) : les trois écritures sont
annulées, `certified / operation_conflict`, rien n'est écrit ; toute autre `IntegrityError` est propagée
après annulation du SAVEPOINT (transaction de l'appelant utilisable, testé).

Contre-épreuves (PostgreSQL 16 et 18) : panne avant l'INSERT événement, après l'INSERT événement, après
l'INSERT attribution, après l'UPDATE de la preuve (pannes `after_flush` : SQL réellement exécuté), violation
**réelle** du CHECK 168 h pendant le flush final, violation **réelle** de la FK d'interaction de
l'attribution, violation **réelle** de la FK preuve → attribution : à chaque fois aucun événement, aucune
attribution, preuve `certified` identique (même `xmin`), puis retry propre → `recorded`. Contrôle après chaque
test : aucun événement certifié sans attribution, aucune attribution sans preuve `recorded` concordante,
aucune preuve `recorded` sans attribution.

## 8 bis. Ultime horloge après les écritures (R1)

Défaut établi par l'audit et **démontré** sur le HEAD `2053abe` : la finalisation lit son horloge après les
verrous explicites, puis l'INSERT de l'événement attend l'entrée d'index unique d'un écrivain hors service
non committé ; si l'attente franchit l'échéance et que l'écrivain annule, l'INSERT réussit et la preuve
passait `recorded` sur une décision périmée. Contre-épreuve (PostgreSQL réel, horloge réelle, aucun
`lock_timeout` atteint) : `close_by_at = window_end_at` à quelques secondes ; attente **observée** sur
l'index unique (`pg_stat_activity` : `wait_event = transactionid` pendant `INSERT INTO
product_activity_events`), horloge initiale lue **avant** l'attente (espion sur `proofs.server_clock`),
ROLLBACK de l'écrivain après la borne. Avant correction : événement + attribution + preuve `recorded`
(collision canonique et collision de clé d'idempotence : 2 échecs sur 2). Après correction : aucun
événement, aucune attribution, preuve `indeterminate / finalization_expired`.

```
with db.begin_nested():                          # UN SAVEPOINT, inchangé
    1. INSERT événement ; 2. INSERT attribution ; 3. UPDATE preuve -> recorded
    4. final = clock_timestamp()                 # après toute attente SQL des écritures
       final < instant de décision      -> annulé, certified / technical_uncertainty, rien d'écrit
       final >= finalization_deadline   -> annulé, indeterminate / finalization_expired à `final`
       final >= fin de conservation     -> annulé, rejected / not_authorized à `final` (défense)
                                        # sinon RELEASE : les trois écritures sont conservées
```

- **Instant de décision retenu** : l'horloge lue après tous les verrous explicites (`event.recorded_at`,
  `proof.resolved_at`). Elle est conservée seulement si la décision est **encore admissible** à l'ultime
  horloge, lue après les écritures qui peuvent attendre. Les autres conditions (participation, campagne,
  visite, preuve) sont tenues par les verrous et ne peuvent pas changer entre les deux lectures.
- L'annulation passe par une exception levée **dans** le SAVEPOINT : les trois écritures disparaissent ensemble
  (aucun événement, aucune attribution, aucune preuve `recorded`) ; la résolution éventuelle est une écriture
  distincte, faite ensuite, à l'instant de l'ultime horloge (**jamais antidatée**), `purge_after_at =
  resolved_at + 168 h` (aucune conservation prolongée) ; `certified_at` inchangé.
- L'écrivain hors service qui **committe** : violation d'unicité, comportement inchangé
  (`certified / operation_conflict`, rien d'écrit).
- **Aucun instant de COMMIT n'est garanti** : PostgreSQL ne permet pas de dater le COMMIT dans la
  transaction elle-même. Entre l'ultime horloge et le COMMIT de l'appelant ne restent que le RELEASE du
  SAVEPOINT et le COMMIT, qui n'attendent aucun verrou. Le contrat porte sur la décision admissible après
  les attentes SQL pertinentes.
- Les décisions sans événement (rejets, `indeterminate`) n'écrivent que la preuve, déjà verrouillée
  `FOR UPDATE` : aucune attente après l'horloge.

## 14. Limites et points pour le raccordement

1. **Échéance** (§ 2, § 6) : arbitrage R1 appliqué, `min(window_end_at + 30 min, close_by_at)` ; la fin de
   la visite d'origine ne la raccourcit plus. Règle propre aux preuves certifiées.
2. **Raccordement** : F2 et l'analytics devront partager la même configuration PostgreSQL canonique
   (idéalement le même moteur) ; la frontière C ne le vérifie pas (aucune lecture F2) et le runner n'est pas
   modifié. La finalisation pourra suivre la certification du bloc B (`proof_id` de `register_pending`) ;
   le mode d'appel (synchrone ou différé) reste hors périmètre.
3. **Preuves `pending` / `certified` résiduelles** : leur résolution est explicite, par preuve ; aucune tâche
   de fond ne les parcourt (sélection et ordonnancement : raccordement / lot 2C).
4. **Statistique perdue** sur COMMIT incertain non confirmable, course perdue, échéance dépassée, conflit :
   assumé (« perdre une statistique plutôt qu'inventer une utilisation »).
5. **Deux horloges serveur** (héritées de 2B-1 / B) : `occurred_at` (Python) et `certified_at` /
   finalisation (PostgreSQL) ; un décalage ne peut que refuser (chronologie exigée), jamais antidater.
6. **Unicités** : elles ne survivent pas à la purge des lignes ; après la purge d'une preuve résolue,
   l'événement et son attribution gardent l'unicité canonique jusqu'à leur propre purge (90 j).
7. **Durcissement 2A** (§ 9) : seul changement de comportement de `record_event`, conservateur.
8. **Instant de décision** (§ 8 bis) : `recorded_at` est l'instant de décision lu après les verrous
   explicites, confirmé par l'ultime horloge après les écritures ; l'instant exact du COMMIT n'est pas
   garanti (PostgreSQL ne le permet pas). Une attente d'écriture qui franchit l'échéance perd la
   statistique (preuve `indeterminate`), conformément au principe du cadrage.
