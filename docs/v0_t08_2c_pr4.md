Contradictions examinées (aucune bloquante ; aucun arbitrage figé modifié) :

1. **B2 — motifs du bloc C révélant une corruption.** `finalization._certification_problem` peut rendre
   `source_unverified`, `visit_conflict`, `origin_unverified`, `window_expired` ou `indeterminate /
   technical_uncertainty`. Après le contrôle préalable d'intégrité de ce parcours (forme, rattachements, chronologie),
   ces motifs ne peuvent provenir que d'une donnée stockée hors contrat : la purge exceptionnelle n'admet **que**
   `rejected / not_authorized` et `indeterminate / finalization_expired` ; tout autre motif → `conflict /
   proof_incoherent`, aucune mutation. L'ordre réel du bloc C est appliqué tel quel (testé : retrait avant échéance de
   finalisation).
2. **B1 — campagne active.** Pour une campagne `active`, l'échéance de finalisation `min(window_end_at + 30 min,
   close_by_at)` est toujours ≤ `close_by_at` < échéance commune ; le cas « pending non échue à la finalisation » ne
   peut donc survenir que pour une campagne terminale. Il est néanmoins refusé explicitement (`conflict /
   resolution_unestablished`) pour une campagne non terminale.
3. **Dépendances physiques et FK.** Visites, interactions, preuves et attributions référencent la participation : en
   l'absence de participation, leur absence est garantie. L'ordre de constat est donc preuve → attribution → visite →
   interaction → participation (chaque motif reste atteignable et désigne le traitement encore nécessaire) ; les
   contrôles sont conservés en défense.
4. **Cohorte activée devenue incomplète.** Aucun service ne retire de place (`cohort.py`) : seul un écrivain hors
   service peut la produire ; signalée `cohort_incoherent`.
5. **Instants stockés et horloges.** Comme la PR 3, les instants stockés écrits par l'horloge Python des services
   historiques (`created_at`, `bound_at`…) sont confrontés à l'horloge PostgreSQL de décision ; une date postérieure
   → `unknown / clock_incoherent` (L15).
6. **Coût du contrôle global.** Mesuré à environ 8 000 documents par seconde avec l'analyse stricte systématique (dont
   `strptime` des échéances), le contrôle de 50 000 événements dépassait le budget de 10 s. La classification
   R5 bis a été **réordonnée sans changement de résultat** (§ 10) : l'analyse stricte ne départage plus que les
   documents qui désignent la campagne. Aucune recherche approximative, aucun index, aucune migration.

## 6. Parcours A — terminaison

**Sélection** : `status IN (planned, active) AND close_by_at <= horloge`, OU anomalie de campagne
(`participation_lifecycle._campaign_anomaly`, réutilisée) ; ordre et curseur `(close_by_at, id)` ; lecture seule, sans
verrou, sans OFFSET (table des campagnes de faible cardinalité : parcours séquentiel accepté, L14).

**Matrice** (sous le verrou exclusif, horloge lue après lui) :

| Situation | Issue |
|---|---|
| campagne absente | `absent` |
| politique, statut ou chronologie hors contrat (validation de `participation_retention_deadline`), même déjà terminale | `conflict` (`policy_incoherent` / `retention_incoherent`) |
| horloge antérieure à `created_at`, `activated_at` ou `closed_at` | `unknown / clock_incoherent` |
| `closed` / `cancelled` cohérente | `already_terminal` (`closed_at` jamais modifié) |
| `planned` / `active`, horloge < `close_by_at` | `not_due` |
| `planned` à échéance | `cancelled` (jamais activée : légitime) |
| `active` à échéance | `closed` |

**Écriture** : UN SAVEPOINT, `UPDATE product_campaigns SET status, closed_at = close_by_at WHERE <ligne exactement
photographiée> AND status IN (planned, active) AND close_by_at <= horloge`, exactement une ligne ; seules ces deux
colonnes changent (testé colonne par colonne) ; aucun descendant modifié (`xmin`). Verrous : la seule ligne de campagne
`FOR UPDATE` (séquence testée) ; aucune clé consultative.

**Écritures historiques tardives (L10, inchangées, testées)** : `add_cohort_seat` sur une campagne planned après
`close_by_at` ; `revise_campaign_policies` sur une campagne planned échue (sérialisée avec la terminaison, puis
`CampaignPolicyLocked`) ; `_mark_admission_failure` après la clôture et l'échéance ; activation concurrente franchissant
l'échéance pendant l'attente (la terminaison décide après : `closed`).

## 8. Parcours B — résolutions (B1, B2), preuves terminales et recorded (B3), atomicité

sinon, campagne `closed` / `cancelled` → `rejected / not_authorized` (parcours exceptionnel seulement) ; sinon
`conflict / resolution_unestablished`. `resolved_at` = horloge PostgreSQL réelle après les verrous ; `purge_after_at =
resolved_at + 168 h` ; `certified_at` NULL conservé.

Contre-épreuve B1 (PostgreSQL réel, services génériques, aucune donnée fabriquée) : campagne générique

annulation) anticipée à J+10, horloge J+100 ≥ échéance : `resolve_expired_pending_proof` (bloc C historique, inchangé)
laisse la preuve `pending` ; la PR 3 est `blocked / proof_remaining` ; la PR 4 rend `resolved_and_purged`
(`rejected`, `not_authorized`) — valeurs réellement écrites relues **dans la transaction**, avant le DELETE, sans
journal persistant : statut, motif, `resolved_at` = horloge, `purge_after_at − resolved_at` = 168 h, `certified_at`
NULL ; aucune ligne d'événement ni d'attribution ; puis PR 3 `purged`, puis purge définitive `purged`. Cas `closed` et
`cancelled` testés.

**Certified (B2)** : contexte `finalization._Locked` construit **sous les verrous de ce parcours** (sans
`finalization._lock`) ; `finalization._certification_problem` (ordre réel du bloc C) ; résolutions admises seulement
`rejected / not_authorized` (campagne terminale, participant retiré — avant l'échéance de finalisation, ordre testé) et

certifiée, `_record`, `_lock`, la résolution historique des pending ni l'écrivain certifié d'événements (test : ces
fonctions remplacées par une exception, la purge réussit ; aucune ligne d'événement ni d'attribution).

**Rejected / indeterminate** : jamais résolues de nouveau (aucun UPDATE, séquence testée) ; motif incompatible avec
l'état → `conflict / proof_incoherent` ; horloge antérieure à `resolved_at` → `unknown` ; résolution extrêmement tardive
purgée aussitôt à l'échéance parente (PR 1 encore `not_due`).

**Recorded (B3)** : avant la PR 2, vérification explicite : événement du chemin certifié, exactement une finalité, de

**Atomicité** : UN SAVEPOINT englobant : `_resolve` (son SAVEPOINT interne) → relecture SQL des colonnes écrites

## 9. Parcours B — protocole L0/L1/L2 et compatibilité

```
0. L0 : preuve et, si recorded, attribution et événement : lecture SANS verrou, photographiées en valeurs ;
1. union des clés : finalization.lock_keys(preuve) ∪ event_lifecycle._required_keys(événement, attribution, [preuve]) ;
2. pg_advisory_xact_lock : UN appel trié (common.lock_identities) ;
3. L1 : relecture ; identité différente : conflict ; clé nécessaire non détenue : conflict (jamais acquise) ;
4. participation FOR SHARE ; 5. campagne FOR SHARE ; 6. visite FOR SHARE ; 7. interaction FOR SHARE ;
8. preuve FOR UPDATE ; absente : absent ; photographie ≠ L1 : conflict / dependency_changed, AVANT tout verrou de

9. attribution FOR SHARE ; 10. événement FOR SHARE — références établies en L1 seulement ;
11. L2 : photographie complète sous verrous = L1, sinon conflict / dependency_changed ; validations ;
12. horloge PostgreSQL ; 13. décision et écritures.
```

## 11. Budget de sécurité (R3)

`GLOBAL_SCAN_BUDGET_SECONDS = 10.0` (constante de module, jamais un paramètre) ; horloge **monotone** (`time.monotonic`)
fixée une fois au début de la transaction de traitement, jamais réinitialisée, ne décidant d'aucune échéance, résolution,
clôture ni admissibilité. Contrôlée : avant chaque lecture globale, après chaque document, après la lecture, après
l'attente des verrous de cohorte et de places (avant la seconde lecture), avant le DELETE. Dépassement → `unknown /
scan_budget_exceeded`, aucune mutation. La relecture après COMMIT incertain dispose de son propre budget (même règle).
`lock_timeout` 2 s et `statement_timeout` 5 s (SET LOCAL) inchangés. **Limite (L17)** : une instruction SQL en cours
peut retarder le contrôle suivant ; le budget n'est pas une durée maximale absolue de la transaction.

## 21. Garanties, hypothèses et limites

**Garanties démontrées** (PostgreSQL réel, contraintes en place) : aucune terminaison avant `close_by_at`, fin effective
jamais repoussée ; aucune purge de preuve avant l'échéance de sa campagne, aucune preuve d'intégrité non établie
résolue ni supprimée, aucune résolution hors des deux résolutions admises, aucun événement ni attribution créé, modifié
ou supprimé ; atomicité résolution + suppression ; aucune purge de campagne avec une dépendance physique, une finalité
canonique de la campagne, un document ambigu ou une lecture globale incomplète ; atomicité places → cohorte → campagne ;
aucune donnée F2 modifiée ; succès annoncé seulement sur COMMIT confirmé ; aucune instruction hors bloc de transaction
effectif ; sérialisation avec tous les écrivains conformes listés, sans interblocage dans les scénarios conformes.

**Hypothèses** : les écrivains de finalités autorisés respectent le protocole de verrouillage et vérifient l'existence
des campagnes et participations concernées ; l'horloge PostgreSQL est monotone ; les services historiques ne sont pas
activés avant leur durcissement.

**Limites** :

- **L1** — Raccourcissement volontaire des finalités et non-recréation : hors périmètre.
- **L2** — Résolutions extrêmement tardives : traitement métier fourni par la PR 4 (B) pour les preuves cohérentes ;
  garantie opérationnelle conditionnée à la PR 5 (cadence).
- **L3** — Participations et visites : primitives PR 3 disponibles.
- **L4** — Campagnes : primitives de terminaison et de purge disponibles (PR 4).
- **L5** — Orchestration : PR 5.
- **L6** — Anomalies de conservation : procédure de résolution obligatoire avant activation (`conflict` des trois
  parcours compris).
- **L7** — Durcissement historique du bloc C : avant raccordement.
- **L8** — Compatibilité des futures révisions de finalités certifiées : hors périmètre.
- **L9** — Perte de référence canonique après purge nominale de preuve : **maintenue** (la PR 4 ne la résout pas).
- **L10** — Écritures et rejeux historiques après expiration : étendue aux campagnes planned échues (ajout de place,
  révision de politique), aux places (marque d'échec d'admission après clôture et échéance ; interblocage possible si
  l'appelant verrouille la campagne après la marque, détecté) ; services inchangés.
- **L11** — Protection des dépendances JSON : étendue à la campagne. Reproduit : un écrivain SQL hors service qui écrit
  une référence à la campagne après la seconde lecture globale laisse une référence orpheline ; entre les deux lectures :
  `conflict / dependency_changed`. Avant activation, tous les écrivains autorisés de finalités devront respecter le
  protocole et vérifier l'existence des campagnes et participations ; une protection structurelle devra être conçue
  avant d'autoriser des écrivains non conformes.
- **L12** — Transition vers `completed` : chantier dédié.
- **L13** — Exhaustivité des rapports de la Vague 0 : prérequis avant exploitation.
- **L14** — Capacité et index : en plus de la PR 3, `EXISTS` des visites par campagne en parcours séquentiel, sélection
  B filtrée par jointure (tous les états du registre parcourus dans l'ordre de `campaign_id`) ; chantier d'optimisation
  avant activation (migration dédiée).
- **L15** — Anomalies chronologiques et de participation : étendues aux cohortes, aux places et aux preuves dont
  l'inscription, la certification ou la finalisation recorded suit la clôture (correctif R1 : `unknown`, corruption et
  divergence d'horloges indiscernables) ; invariants inter-horloges
  (instants Python confrontés à PostgreSQL) ; procédure de résolution nécessaire.
- **L16 (nouvelle)** — Réutilisation des codes de campagne après purge : l'UUID demeure l'identité de référence ;
  l'interdiction permanente de réutiliser un ancien code n'est pas garantie sans trace persistante (aucun tombstone) ;
  la non-réutilisation volontaire reste une convention opérationnelle.
- **L17 (nouvelle)** — Capacité et ambiguïté du contrôle global JSON : lecture exhaustive coûteuse (§ 18) ; un document
  indéterminable bloque toutes les campagnes, même sans rattachement connu (relève aussi de L6, L15) ; le budget
  interrompt sans jamais autoriser de suppression partielle ou approximative ; capacité réelle à démontrer avant
  activation ; le budget n'est pas une durée maximale absolue.

Les limites ne sont jamais une autorisation de prolonger la conservation.
