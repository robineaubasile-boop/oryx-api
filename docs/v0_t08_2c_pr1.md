## 3. Contrat des interfaces

### Service (`core.product_analytics.proof_lifecycle`, la transaction appartient à l'appelant)

| Fonction | Entrée | Sortie | Écrit |
|---|---|---|---|
| `select_certified_candidates(db, *, limit=50, after=None)` | `limit` entier exact 1..200 ; `after` : `ProofCursor` de la même sélection ou `None` | `CandidatePage(selection, proof_ids, next_cursor)` | jamais |
| `select_expired_pending_candidates(db, *, limit=50, after=None)` | idem | idem | jamais |
| `select_purgeable_candidates(db, *, limit=50, after=None)` | idem | idem | jamais |
| `purge_resolved_proof(db, *, proof_id)` | `uuid.UUID` seulement | `PurgeDecision(outcome, reason, written, state)` | une ligne du registre au plus, dans un SAVEPOINT (flush, jamais COMMIT) |
| `observe_purge(db, *, proof_id)` | `uuid.UUID` | `PurgeDecision(present / absent)` | jamais |
| `purge_problem(proof, now)` | ligne et instant | motif ou `None` | — |

Aucune interface n'accepte d'horloge (`now`), d'identité métier, de propriétaire, de `force` ni d'option de
contournement (testé : `TypeError` / `InvalidProductAnalyticsInput` avant tout accès à la base). L'horloge est
toujours `clock_timestamp()` PostgreSQL (`proofs.server_clock`).

### Frontière (`core._activity_proof_lifecycle`, une transaction par preuve)

| Fonction | Traitement |
|---|---|
| `recover_certified_proof(engine, *, proof_id)` | `finalization.finalize_certified_proof` via `_activity_event_finalization._run` |
| `expire_pending_proof(engine, *, proof_id)` | `finalization.resolve_expired_pending_proof` via `_activity_event_finalization._run` |
| `purge_proof(engine, *, proof_id)` | `proof_lifecycle.purge_resolved_proof`, COMMIT, relecture si COMMIT incertain |
| `recover_certified_page` / `expire_pending_page` / `purge_resolved_page(engine, *, limit=50, after=None)` | **une** page : sélection (transaction de lecture courte, terminée), puis chaque candidat dans sa propre transaction |

**Propriété de la transaction (contrat).** La frontière n'annonce une écriture (`finalized`, `resolved`,
`purged`) que pour une transaction qu'elle a **elle-même** ouverte et committée. Chacun des six points
d'entrée exige donc un `sqlalchemy.Engine` PostgreSQL synchrone, à partir duquel elle ouvre une transaction
autonome par preuve (et une pour la sélection) :

| Argument `engine` | Comportement |
|---|---|
| `Engine` PostgreSQL synchrone, isolation transactionnelle (y compris `execution_options` compatibles) | accepté |
| `Connection` ou `Session` de l'appelant, avec ou sans transaction ouverte | `TypeError` avant toute connexion : aucune instruction (pas même `BEGIN`), transaction de l'appelant inchangée (même `txid`, ni committée ni annulée) |
| `None`, URL (texte ou `URL`), objet quelconque, moteur non PostgreSQL ou asynchrone | `TypeError` avant toute connexion |
| `Engine` en `AUTOCOMMIT` (`create_engine(isolation_level=…)` ou `execution_options(isolation_level=…)`), ou `postgresql_readonly` | `TypeError` avant toute connexion |
| `Engine` dont le pilote est mis en autocommit hors de SQLAlchemy (événement `connect`, invisible à l'examen statique) | dans **chaque** transaction, après les garde-fous du bloc C et avant tout travail, libpq doit rapporter un bloc de transaction effectif (`PQTRANS_INTRANS`) ; sinon rien n'est lu, verrouillé ni écrit : `unknown` (page : `selected = False`) |

**Aucune transaction n'hérite de la validité d'une autre.** Chaque transaction (sélection, écriture, relecture
d'un COMMIT incertain de purge **ou du bloc C**) est une session distincte : elle peut emprunter une autre
connexion physique du même `Engine`, dans un autre état. La vérification d'une transaction antérieure ne
garantit donc jamais celle d'une transaction ultérieure ouverte sur le même moteur ; chacune est vérifiée
pour elle-même, au moment où elle commence.

Avant correction (HEAD `99ea9c1`, mesuré sur PostgreSQL réel) : une `Connection` portant une transaction
fraîche de l'appelant donnait `purge_proof → purged`, `recover_certified_proof → finalized`,
`expire_pending_page → resolved = 1`, alors qu'une connexion indépendante voyait toujours la preuve inchangée
et que le ROLLBACK de l'appelant l'annulait : succès annoncé sans COMMIT de la frontière (la `Session` interne
rejoint la transaction externe, son `commit()` n'est pas celui de PostgreSQL). En AUTOCOMMIT, verrou
consultatif et `FOR UPDATE` étaient pris hors de tout bloc (relâchés aussitôt) ; seul l'échec du SAVEPOINT
empêchait l'écriture. Le correctif est confiné à `core/_activity_proof_lifecycle.py` ; la frontière historique
du bloc C (`core/_activity_event_finalization.py`) était alors inchangée.

Second correctif (audit de `f65c842`) : la relecture `observe_proof` qu'ouvre le bloc C après un COMMIT
incertain de reprise ou de résolution n'était pas contrôlée (seule l'écriture l'était, `_owned(work)`). Mesuré
sur PostgreSQL réel avec une écriture effectivement transactionnelle, COMMIT réellement effectué mais
confirmation perdue, puis connexion de relecture mise en autocommit par le pilote : la relecture exécutait hors
de tout bloc les garde-fous, quatre `pg_advisory_xact_lock` (relâchés à chaque instruction) et neuf lectures
métier (registre, participation, campagne, session, interactions, événement, attribution), puis annonçait
`finalized` (`recover_certified_page` : `finalized` = 1) ou `resolved` (`expire_pending_page` : `resolved` = 1).
Après correction : `unknown / technical_uncertainty`, seuls les trois `SET` des garde-fous hors bloc, aucune
lecture métier ni verrou, aucun compteur de succès (`unknown` = 1).

Extension minimale du bloc C, seule voie sans dupliquer l'établissement du COMMIT incertain : cette relecture
est ouverte **à l'intérieur** de `_activity_event_finalization._establish`, hors d'atteinte de la frontière 2C.
Les autres voies (réécrire `_establish` ; remplacer `finalization.observe_proof` dans le module, global et
visible des appelants historiques ; un hook d'événement sur le moteur, état partagé avec eux) sont écartées.
`_run` et `_establish` reçoivent un paramètre nommé facultatif `observe` ; `None` (valeur par défaut) désigne
`finalization.observe_proof`, résolue à l'appel : `finalize_in_transaction` et `expire_pending_in_transaction`
ne le passent pas et gardent strictement leur comportement (relecture non contrôlée, testée). La frontière 2C
passe `observe=_owned(finalization.observe_proof)`. Aucune autre ligne du bloc C ne change.

Rendus : `LifecycleOutcome(outcome, state, reason)` (aucun identifiant) et `PageReport(selection, selected,
examined, finalized, resolved, purged, absent, still_present, not_admissible, conflict, unknown, next_cursor)`.
Aucune fonction ne lève (sauf entrée invalide, avant toute connexion). Aucune boucle sur plusieurs pages :

| `not_admissible` | rien à faire sous verrou : pending non expirée, déjà résolue (y compris par un concurrent), recorded idempotente, non terminale, non échue, échéance incohérente, horloge incohérente | `not_admissible` |

comptée comme committée : l'attribution à « ce traitement » exige `decision.written` **et** une issue établie

## 5. Sélection, pagination et bornes

| Sélection | Filtre (horloge PostgreSQL) | Ordre / curseur | Index réellement utilisé |
|---|---|---|---|
| `certified_recovery` | `status = 'certified'` (toutes : finalisables ou à résoudre) | `(created_at, id)` | aucun index dédié : parcours séquentiel ou `ix_product_activity_proof_registry_campaign_status` en filtre (colonne non initiale) |
| `pending_expiry` | `status = 'pending'` et `least(window_end_at + 30 min, close_by_at) <= horloge` (jointure participation, campagne) | `(created_at, id)` | aucun index dédié (jointures par clés) |
| `resolved_purge` | `purge_after_at IS NOT NULL AND purge_after_at <= horloge AND status IN terminaux` | `(purge_after_at, id)` | **`ix_product_activity_proof_registry_purge_after_at`** (partiel `purge_after_at IS NOT NULL`), parcours borné dans l'ordre de l'index, borne inférieure du curseur dans la condition d'index (EXPLAIN testé sur 16 et 18) |

- Taille de page : entier exact (`bool`, `float`, `str` refusés), 1 ≤ `limit` ≤ 200, défaut 50 (limites
  opérationnelles proposées, pas des décisions produit). `LIMIT` SQL : aucun chargement non borné.
- Pagination par **curseur de position** (`ProofCursor`, position et identifiant du dernier candidat rendu,
  dépassés strictement : `(position, id) > curseur`), jamais `OFFSET`. `next_cursor` présent quand la page est
  pleine ; absent quand la sélection est épuisée. Ordre total déterministe (départage par `id`, testé sur 205
  preuves de même échéance).
- **Famine** : le curseur avance quelle que soit l'issue de chaque candidat ; une ligne en échec (délai de
  verrou) n'est rendue qu'une fois par passe et ne masque jamais les suivantes (testé, pages de 1 et page
  complète). Les preuves non éligibles (pending non expirées, terminales non échues) ne sont jamais rendues ;
  une `certified` expirée est résolue au premier passage puis disparaît de la sélection (pas de retry infini).
- La sélection est une lecture **sans verrou**, répétable, sans écriture (testé, `xmin` compris) ; elle ne
  vaut jamais autorisation : chaque candidat est relu sous verrou.
- Index : la sélection de purge (la seule qui croît avec le temps) est servie par un index existant. Les
  deux autres portent sur des preuves **résiduelles** (normalement finalisées ou résolues sans délai) dans un
  registre lui-même borné par les 168 heures ; un index `(status, created_at, id)` partiel pourra être
  arbitré si les volumes le justifient. **Aucune migration** dans cette PR.

## 7. Transactions et COMMIT incertain

- Le service ne fait jamais `commit()` / `rollback()` ; la suppression est un DELETE conditionnel dans un
  SAVEPOINT (`rowcount` ≠ 1 → SAVEPOINT annulé, `conflict / delete_unconfirmed`).
- La frontière réutilise `_activity_event_finalization._transaction` (READ COMMITTED, `lock_timeout` 2 s,
  `statement_timeout` 5 s en `SET LOCAL`) : **une transaction par preuve**, plus une transaction de lecture
  pour la sélection. Un échec isolé ne compromet aucun autre candidat.
- La frontière possède chaque transaction dont elle annonce l'issue (§ 3) : moteur exigé, refus statique des
  `Connection` / `Session` / AUTOCOMMIT / lecture seule, puis contrôle `PQTRANS_INTRANS` au début de chaque
  transaction de sélection, d'écriture, de relecture de purge **et** de relecture d'un COMMIT incertain du
  bloc C (`observe=_owned(finalization.observe_proof)`). La validité d'une transaction antérieure ne garantit
  jamais celle d'une transaction ultérieure ouverte sur le même moteur (autre connexion physique possible).
- Reprise / résolution : l'issue du COMMIT (y compris incertain) est établie par `_activity_event_finalization`
  (relecture `observe_proof` sous les mêmes verrous), inchangée. Garanties R1 du bloc C conservées (ultime
  horloge après les écritures, dans le SAVEPOINT).

| Issue de la transaction de purge | Rapport |
|---|---|
| COMMIT confirmé | décision du service (`purged`, `absent`, `not_admissible`, `conflict`) |
| rien supprimé (même si la confirmation est perdue) | décision lue sous verrou |
| COMMIT incertain, relecture (nouvelle transaction, même clé : une transaction encore active est attendue) : preuve absente | `absent / unconfirmed_commit` — elle n'est plus présente, **sans** attribuer la suppression à ce traitement |
| COMMIT incertain, preuve encore présente | `still_present / technical_uncertainty` — réexécution explicite sûre |
| COMMIT incertain, relecture impossible | `unknown` |
| panne avant COMMIT, délai, interblocage, base injoignable | `unknown` ; rien n'est committé |

Aucun retry automatique ; aucune preuve n'est jamais recréée pour résoudre une incertitude. La réexécution
explicite (même preuve ou même page) est sûre et idempotente (testé).

## 8. Horloges

- Toutes les décisions utilisent `clock_timestamp()` PostgreSQL lu **après** les verrous ; la sélection lit la
  même horloge (indicative) ; aucune interface n'accepte d'horloge de l'appelant.
- Attente de verrou franchissant l'échéance : la sélection, avant l'échéance, ne rend pas la preuve ; une
  purge qui attend la clé pendant le passage de l'échéance décide après l'attente et supprime (horloge
  PostgreSQL **réelle**, testé). Inversement, une décision de purge n'est jamais prise sur une horloge lue avant
  une attente.
- Horloge régressive : `horloge < resolved_at` → `clock_incoherent`, rien supprimé ; candidat sélectionné
  puis horloge reculée sous l'échéance → `not_due` (testé). Aucune résolution antidatée : la résolution d'une
  pending traitée tardivement porte l'instant réel de traitement (testé : échéance + 2 h).
- **168 heures absolues** : la garde SQL du DELETE utilise `make_interval(secs => 604800)`. Constat établi
  par les tests : psycopg2 transmet un `timedelta(hours=168)` comme `'7 days'`, que PostgreSQL ajoute en
  **jours civils** du fuseau de session (167 ou 169 heures aux changements d'heure). La première version liait
  le `timedelta` : sous Europe/Paris et America/New_York la garde refusait (aucune suppression, mais
  `conflict`). Corrigé avant la PR ; contre-épreuve conservée dans le test des fuseaux.

## 9. Conservation et indépendance des données définitives

- Supprimable **si et seulement si** : statut terminal, `resolved_at` et `purge_after_at` renseignés,
  `purge_after_at = resolved_at + 168 h`, `purge_after_at <= clock_timestamp()` (égalité admise ; −1 µs : rien).
  Jamais de modification de `resolved_at` / `purge_after_at`, jamais de durée recalculée (lecture, retry,
  panne, lancement, certification).
- Testé pour chacun des trois états terminaux : 168 h − 1 µs conservée (ligne identique, `xmin` compris),
  168 h exactement supprimée, au-delà supprimée, absente idempotente ; `pending` et `certified` refusées même
  400 jours plus tard ; échéance incohérente refusée (CHECK retiré **dans** une transaction de test annulée :
  167 h, 169 h, 7 jours civils à Paris) ; fuseaux UTC, Europe/Paris, America/New_York, passages à l'heure
  d'hiver (25/10/2026, 01/11/2026) et d'été (28/03/2027, 14/03/2027) : 168 h absolues, heure murale 167 h / 169 h.

## 14. Limites à arbitrer pour les PR suivantes

**A — Conservation raccourcie d'un événement (avant la PR 2).** Une preuve `recorded` référence son
attribution par une FK non différable, sans cascade. Tant qu'elle est conservée (au plus 168 h après la
finalisation, elle-même au plus `window_end_at + 30 min`), l'attribution — donc l'événement — ne peut pas être
supprimé. En conservation nominale il n'y a pas de conflit (`purge_after_at` de la preuve ≤ J0 + 19 j 30 min
≪ 90 jours). Le conflit n'apparaît que si la conservation de l'événement est **raccourcie** (révision de
finalité, effacement). Options, aucune implémentée :
1. subordonner la preuve à l'échéance la plus courte : supprimer dans **une** transaction la preuve,
   l'attribution puis l'événement, avant les 168 h (la durée de 0024 devient un maximum) — **recommandée** ;
2. différer la suppression de l'événement jusqu'à la purge de la preuve — **exclue** (prolongation) ;
3. `ON DELETE CASCADE` / `SET NULL` ou nouvel état — migration et révision du CHECK d'état, **exclue** ici.
Point technique pour la PR 2 : le DELETE d'une attribution contrôle le registre (FK NO ACTION, verrou
`FOR KEY SHARE` sur la ligne référençante). La PR 2 devra donc acquérir **toutes** les clés consultatives de
preuve (`activity_proof`) **et** d'événement **ensemble**, en un seul appel `common.lock_identities`, dans
l'ordre global trié (celui du bloc C), avant tout verrou de ligne — jamais la clé de preuve puis les clés
d'événement en deux temps, ni l'inverse, qui ouvrirait un cycle avec le bloc C ou avec cette purge. Cette note
ne change pas le périmètre de la PR 1 (aucune suppression d'événement ni d'attribution ici).

**B — Résolution extrêmement tardive (avant la PR 4).** Sans exécution périodique (PR 5), une preuve
`pending` / `certified` peut rester non résolue longtemps ; sa résolution porte l'instant réel (jamais
antidaté) et `purge_after_at = résolution + 168 h`, qui peut dépasser l'échéance des données de campagne. Le
registre référence participation, visite et interaction (FK sans cascade) : la purge de campagne (PR 4) serait
bloquée jusqu'à cette échéance. Options : (1) objectif opérationnel de la PR 5 — reprise bornée après
l'échéance de finalisation, donc `purge_after_at ≤ close_by_at + délai + 168 h` ; (2) purge de campagne
supprimant d'abord, sous la clé `activity_proof`, les preuves terminales de la campagne quelle que soit leur
échéance (168 h comme maximum) ; (3) pour une preuve encore non résolue à la purge de campagne : résolution
puis suppression dans la même transaction. Ni antidatage, ni prolongation de campagne.

**C — Révision des finalités** : `retention.validate_scope_revision` existe ; aucune révision effective ici.

**D — Raccordement** : le bloc C reçoit toujours un `proof_id` interne ; la frontière B et F2 ne sont pas
modifiées pour le transmettre.

Autres limites :
1. **Unicité canonique après purge** (héritée, PR 3 § 14.6) : après la purge d'une preuve, une nouvelle
   preuve de la même opération ne peut naître que d'une opération F2 établie comme **nouvelle** (un rejeu est
   `no_new_effect`) ; l'événement et l'attribution gardent l'unicité canonique jusqu'à leur propre purge.
2. **Index** des sélections `certified` / `pending` (§ 5) : à arbitrer selon les volumes, sans migration ici.
3. **Statistique perdue** sur COMMIT incertain non confirmable, course perdue, délai de verrou : assumé.
4. **Frontière historique du bloc C** (`finalize_in_transaction`, `expire_pending_in_transaction`) : sans
   appelant, comportement inchangé ; elle n'exige pas de moteur et ne contrôle pas ses transactions. Seule

   d'entrée ne passent pas. Le cycle de vie ne les appelle jamais, seulement `_run` / `_transaction`
   derrière ses propres contrôles.
5. **Horloge des tests de chaîne** : les 168 heures sont simulées en décalant `proofs.server_clock` (horloge
   PostgreSQL + décalage) ; les bornes exactes sont testées avec l'horloge déterministe, l'attente franchissant
