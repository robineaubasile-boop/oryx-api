## 4. Vocabulaires et compteurs

|---|---|---|
| `pruned` | finalités expirées retirées **par ce traitement**, COMMIT **confirmé** | `pruned` |
| `purged` | événement (+ attribution, + preuve) supprimés **par ce traitement**, COMMIT **confirmé** | `purged` |
| `not_due` | aucune finalité échue sous verrou | `not_due` |

| `unknown` | panne, délai, interblocage, base injoignable, horloge incohérente, relecture impossible ou état différent | `unknown` |
| `unconfirmed` | COMMIT incertain d'un retrait, état révisé attendu observé — **jamais** `pruned` | `unconfirmed` |
| `still_present` | COMMIT incertain, état initial intact observé (constat, pas preuve d'absence de COMMIT) | `still_present` |

exactement une ligne. Toutes les autres colonnes identiques (testé colonne par colonne, `xmin` des lignes

## 8. Temporalité

- Horloge : `proofs.server_clock` (`clock_timestamp()`), lue après les verrous ; la sélection la lit aussi
  (indicative). Aucune horloge de l'appelant.
- Bornes : −1 µs `not_due` (ligne identique, `xmin` compris) ; égalité `purged` ; au-delà `purged`.
- Attente de verrou franchissant l'échéance (horloge PostgreSQL **réelle**) : la sélection ne rend pas
  l'événement avant ; l'expiration attend les clés pendant le passage de l'échéance et supprime.
- Horloge régressive (< `updated_at`) : `unknown / clock_incoherent`, rien écrit.
- Fuseaux de session UTC, Europe/Paris, America/New_York, 90 jours franchissant l'heure d'hiver (25/10/2026,
  01/11/2026) et d'été (28/03/2027, 14/03/2027) : échéance = `occurred_at` + 2160 h absolues, décision identique
  ; contre-épreuve : `+ interval '90 days'` en jours civils diffère sous Paris / New York. Aucun intervalle SQL
  n'est utilisé (le défaut de la PR #255 ne peut pas se reproduire : seules des valeurs `timestamptz` absolues
  sont liées).
- Aucun statut `withdrawn`, `closed`, `cancelled` n'avance une échéance (testé).

## 9. Atomicité et suppressions

```
with db.begin_nested():                                  # UN SAVEPOINT
    DELETE preuve recorded référençante (si présente)    # id, statut, recorded_event_id, identité, dates
    DELETE attribution (si certifié)                     # event_id, identité, certified_at
    DELETE événement                                     # identité, document, échéances, updated_at, purge_after_at <= horloge
    # chacun : exactement une ligne, sinon annulation du SAVEPOINT (write_unconfirmed)
```

- La preuve ne prolonge jamais la conservation de l'événement ; elle n'est supprimée avant ses 168 heures que si
  elle référence exactement l'attribution de l'événement intégralement échu et concorde (§ 5). Ni `resolved_at`
  ni `purge_after_at` de la preuve ne sont modifiés ; `purge_resolved_proof` (PR 1) n'est ni appelée ni changée.
- Aucune preuve `pending`, `certified`, `rejected`, `indeterminate` n'est supprimée par ce mécanisme (testé).
- Pannes injectées après chaque `DELETE`, après l'`UPDATE` et au `RELEASE` ; nombre de lignes inattendu sur chacune
  des trois tables ; prédicat qui ne correspond à rien : aucune écriture durable, `xmin` intacts, réexécution
  propre. `IntegrityError` dans le SAVEPOINT : `conflict / dependency_changed`.
- FK inchangées (`NO ACTION`, non différables), ni `CASCADE`, ni `SET NULL`, ni tombstone ; séquence exacte des
  instructions testée (un SAVEPOINT, trois `DELETE` dans l'ordre, aucun `UPDATE` / `INSERT`).

## 10. Propriété transactionnelle et COMMIT incertain

- Les quatre points d'entrée exigent un `Engine` PostgreSQL synchrone transactionnel : `Connection` / `Session`
  (fraîche ou déjà utilisée), `None`, URL, SQLite, `AUTOCOMMIT` configuré (moteur ou option), lecture seule →
  `TypeError` avant toute connexion, aucune instruction, transaction de l'appelant intacte (même `txid`).
- `PQTRANS_INTRANS` vérifié dans **chaque** transaction (sélection nominale, traitement, sélection d'intégrité,
  inspection, relecture après COMMIT incertain), par `_owned` ; AUTOCOMMIT imposé au pilote : `unknown`, aucune
  lecture d'événement, aucun verrou, aucune écriture ; AUTOCOMMIT imposé à la **seule** connexion de relecture :
  `unknown`, seuls les `SET` des garde-fous hors bloc, aucun compteur de succès.

| Transaction d'écriture | Rapport |
|---|---|
| COMMIT confirmé | décision du service (`pruned`, `purged`, …) |
| rien écrit (même si la confirmation est perdue) | décision lue sous verrou |
| COMMIT incertain → relecture (nouvelle transaction, clés de l'opération tentée) : événement absent | `absent / unconfirmed_commit` |
| état révisé attendu observé | `unconfirmed / unconfirmed_commit` (jamais `pruned`) |
| état initial intact | `still_present / technical_uncertainty` (réexécution explicite sûre) |
| état différent, relecture impossible | `unknown` |
| panne avant COMMIT, délai, interblocage, base injoignable | `unknown` ; rien n'est committé |

Testé : COMMIT effectué / non effectué / confirmation perdue pour la purge et le retrait ; retrait concurrent
identique après un COMMIT incertain non effectué → `unconfirmed` (l'état attendu ne prouve pas l'origine).

  contrôlés), aucune réparation, aucun stockage. Détecte notamment : élément de document invalide, colonnes ≠
