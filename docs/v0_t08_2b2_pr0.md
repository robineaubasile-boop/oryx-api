# V0-T08 Lot 2B-2 — PR 0 : attestations métier internes F2 (dormantes)

## 1. Référentiel et périmètre

Prérequis technique isolé du lot 2B-2. Il n'implémente **aucun** des blocs analytics
(A : registre provisoire, B : certification après commit, C : finalisation atomique).

Objectif unique : permettre au code interne F2 de distinguer une opération métier réellement
nouvelle et effective d'un rejeu ou d'une opération sans effet, pour :

- **Décrypter** : premier ACK effectif (`pending -> delivered`) ou ACK rejoué ;
- **Portfolio** : création, modification effective, suppression, modification sans effet (no-op),
  rejeu d'un reçu déjà committé.

`main` vérifié avant toute modification : `c6e2d1068d88ce2525348f113a780d039136cbce` (PR #249).

## 2. Contrat d'attestation (`core/authz_f2/attestations.py`, module pur)

`BusinessAttestation` : dataclass gelée, `slots`, **quatre champs exacts** :

| Champ | Type | Origine |
|---|---|---|
| `owner_user_id` | `str` | `ctx.principal.user_id` (principal F2 autorisé, jamais un `user_id` client) |
| `operation` | `str` (fermé) | nature exacte de l'opération |
| `operation_id` | `uuid.UUID` | identifiant canonique de l'opération |
| `qualification` | `str` (fermé) | branche métier réellement exécutée |

Vocabulaire et couples fermés (`ADMISSIBLE`) :

| `operation` | `operation_id` | qualifications admises |
|---|---|---|
| `decryptage_delivery_ack` | `assistant_turn_id` (la livraison) | `delivery_first_ack`, `delivery_replay` |
| `portfolio_position_create` | `operation_id` du reçu | `portfolio_created`, `portfolio_replay` |
| `portfolio_position_update` | `operation_id` du reçu | `portfolio_updated`, `portfolio_noop`, `portfolio_replay` |
| `portfolio_position_delete` | `operation_id` du reçu | `portfolio_deleted`, `portfolio_replay` |

Les natures portefeuille sont les `operation_type` des reçus : `(owner_user_id, operation,
operation_id)` est exactement le triplet unique de `portfolio_write_idempotency`. Une attestation
n'est donc jamais interchangeable entre deux opérations ou deux utilisateurs. Aucune valeur financière
n'entre dans l'identité.

`new_effect` est vrai seulement pour `delivery_first_ack`, `portfolio_created`, `portfolio_updated`,
`portfolio_deleted` : les no-op et les rejeux ne sont jamais des utilisations nouvelles.

Aucune donnée financière, aucun contenu IA, aucune donnée d'authentification (ni session, ni génération,
ni secret), aucune date. `repr` n'affiche ni le propriétaire ni l'identifiant.

Les fabriques (`delivery_ack`, `portfolio`) sont **totales** : une entrée hors contrat rend `None`
(statistique perdue), jamais une exception.

## 3. Transport et exposition

- Les adaptateurs enveloppent la valeur métier **inchangée** dans `Attested(value, attestation)`
  (données, aucun rappel, aucune validation à la construction).
- Le runner retire l'enveloppe (`att.unwrap`) **juste après** `spec.execute`, **avant** les contrôles
  `ABSENT` / `CONFLICT` / `IDEMPOTENCY_CONFLICT` : la valeur examinée et rendue est exactement
  l'historique.
- `run(credential, command)` garde son contrat exact (`AuthorizationOutcome` à trois champs, mêmes
  statuts, mêmes journaux) ; la surface publique du runner reste `{"run"}`.
- Exposition interne séparée, **privée, sans aucun appelant** : `_run_attested(credential, command) ->
  AttestedOutcome(outcome, attestation)`. `outcome` est celui que `run()` aurait rendu.
- L'attestation n'est retenue (`_retain`) qu'**après la sortie du bloc transactionnel**, donc après un
  COMMIT confirmé, pour un résultat `AUTHORIZED`, et seulement si elle est liée au principal et à la
  commande exécutés (`_adapters.ATTESTED_COMMANDS`, `attestations.bound`). Sinon elle est abandonnée
  (journal `attestation=dropped`, sans détail) ; l'opération n'en dépend jamais.
- ROLLBACK, refus, exception, COMMIT refusé ou incertain : aucune attestation.

## 4. Décrypter : preuve du premier ACK

Dans le pont (`_decryptage_orm_bridge._acknowledge`), sur le **seul chemin attesté**
(`AckAdmissionPort`) :

1. `ad.lock_owned_delivery` : `SELECT ... FOR UPDATE` avec `populate_existing` (dernière version
   committée, relue après l'attente du verrou, READ COMMITTED) ;
2. contrôles d'attestation C2 inchangés (identité, runtime V2, lien V2 verrouillé, couple
   `pending/awaiting_delivery` ou `delivered/captured`) ;
3. **`first_ack = delivery.status == ad.PENDING`**, lecture d'attribut, avant toute mutation ;
4. provenance, capture, `pending -> delivered`, flush : inchangés ;
5. la vue `DeliveryAcknowledged` est construite à l'identique (trois champs) et enveloppée.

Tant que la transaction tient ce verrou, aucun autre ACK (C2 ou historique) ne peut effectuer la
transition : `pending` observé sous verrou + COMMIT confirmé = cette transaction a effectué la transition
exactement une fois. La nouveauté n'est jamais déduite du statut final (`delivered` dans les deux cas)
ni de la preuve C1-B (`_canonical_proof`), lue avant le verrou de la livraison : un ACK historique
concurrent peut l'avoir rendue obsolète. Le test
`test_the_qualification_comes_from_the_locked_delivery_not_from_the_pre_lock_proof` le démontre : la
preuve voit `pending`, l'attestation (sous verrou) est `delivery_replay`.

L'adaptateur `_acknowledge_delivery` retire l'enveloppe puis applique **à l'identique** son contrôle
historique à la vue nue ; le chemin historique (sonde `TransactionProbe`) rend toujours la vue nue.

## 8. Limites résiduelles

- **COMMIT incertain** : l'opération a pu être committée sans confirmation ; aucune attestation n'est
  rendue (statistique perdue). L'ACK suivant observe `delivered` sous verrou et est qualifié
  `delivery_replay` ; le rejeu portefeuille est `portfolio_replay`. Perte assumée, conforme à la
  priorité « préserver F2 ».
- L'attestation est une valeur Python en mémoire, non scellée cryptographiquement : sa seule source
  admise est `_run_attested`. Le bloc B devra la consommer depuis cette sortie, jamais depuis une donnée
  extérieure.
- `_run_attested` est privé (la surface publique figée du runner reste `{"run"}`) ; l'exposer sous un nom
  public pour le bloc B est une décision d'architecture laissée au fondateur.
- Chemin historique de l'ACK (banc d'essai PR 9-A, sonde `TransactionProbe`) : non attesté, par
  construction.

## 9. Correctif d'audit : construction et transport des enveloppes totaux

Constat de l'audit indépendant : les fabriques d'attestation étaient protégées, mais pas la construction
(`att.attach()` dans le pont et l'adaptateur portefeuille, `att.Attested(...)` dans l'adaptateur ACK) ni
l'extraction (`att.unwrap()` dans le runner et l'adaptateur ACK). Une exception à ces endroits, levée
dans la transaction métier, aurait provoqué ROLLBACK puis UNAVAILABLE pour une opération qui devait
réussir.

Correction minimale (aucun appelant ni aucune architecture modifiés) :

| Point | Avant | Après |
|---|---|---|
| Enveloppe | dataclass `Attested` (lecture par attributs) | `Attested(tuple)` : tuple natif `(valeur, attestation)` |
| `attach` | construction sans garde | **total** : `tuple.__new__` puis vérification (type exact, taille, valeur et attestation restituées à l'identique) ; toute panne rend **la valeur d'origine** (même objet) |
| Adaptateur ACK | `att.Attested(outcome, attestation)` | `att.attach(outcome, attestation)` |
| `unwrap` | lecture `value.value` / `value.attestation` | **total** pour toute valeur métier : type exact, puis `tuple.__len__` / `tuple.__getitem__` (aucune méthode redéfinissable) |
| `delivery_ack`, `portfolio`, `bound` | garde partielle | corps entier sous garde ; toute anomalie : `None` / `False` |

Une enveloppe de taille inattendue ne peut pas sortir d'`attach`, qui vérifie la taille à la construction.
Si une telle enveloppe apparaissait malgré tout, sa valeur métier ne serait pas restituable : `unwrap`
oppose alors un refus fermé (ROLLBACK et UNAVAILABLE). Il ne rend jamais une enveloppe ni une valeur
substituée comme résultat public.

Injection de pannes (unitaires et PostgreSQL 16 / 18) :

| Panne | Point visé | Attendu et vérifié |
|---|---|---|
| `attestation_init` | construction du contrat | opération réussie, résultat public identique, attestation `None` |
| `factory_build` | fabrique interne | idem |
| `envelope_type` | construction de l'enveloppe | idem |
| `envelope_verification` | vérification de l'enveloppe | idem |
| `binding` | liaison au principal après COMMIT | idem |
| `foreign_object` | objet transporté qui n'est pas une attestation | idem, aucune fausse attestation exposée |
| `envelope_accessors` | méthodes redéfinissables de l'enveloppe | transport intact, attestation correcte (jamais utilisées) |

Opérations couvertes :
- ACK : premier ACK et rejeu ;
- Portfolio : création, modification, no-op, suppression et rejeu.

Contrôles effectués pour chaque panne et chaque opération :
- `run()` rend exactement le même résultat ;
- les octets HTTP de l'ACK sont identiques ;
- le reçu canonique est exact ;
- le texte SQL exécuté est identique à celui de la même opération sans panne : mêmes instructions, donc mêmes verrous ;
- les refus F2 (NOT_FOUND, REVISION_CONFLICT, IDEMPOTENCY_CONFLICT) et les ROLLBACK métier légitimes sont inchangés sous chaque panne.
