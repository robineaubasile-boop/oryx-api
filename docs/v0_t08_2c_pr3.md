Contradictions examinées (aucune n'est bloquante ; aucune ne modifie un arbitrage figé) :

1. **Capacité de la purge (R2, L14)** : le schéma 0023 ne fournit pas d'index de soutien à la FK
   `product_activity_session_interactions_session_fkey` (`session_id` n'est en tête d'aucun index) ni d'index
   `(campaign_id, user_id)` sur les visites. La suppression d'une visite déclenche un contrôle de FK qui parcourt les
   entrées d'index des interactions du couple : coût ∝ visites × interactions. Mesuré : 50 000 interactions sur 500
   visites 1,3 s ; sur 25 000 visites, dépassement du `statement_timeout` de 5 s → `unknown`, rien n'est supprimé
   (§ 13). Une migration étant exclue, ce point est documenté comme **prérequis bloquant avant activation pour de tels
   volumes** ; ni timeout modifié, ni purge fractionnée.
2. **Anomalies JSON (R5)** : « réutiliser `retention.parse_retention_scopes` » et « distinguer les anomalies
   pertinentes des anomalies indépendantes » ne sont conciliables que si un document refusé par l'analyse stricte peut
   encore être lu structurellement. Proposition appliquée, **à valider à l'audit** : analyse stricte d'abord ; en cas de
   refus, lecture structurelle tolérante (`scopes` liste d'objets portant un `campaign_id` UUID) servant **uniquement à
   exclure** la campagne traitée, jamais à autoriser une suppression qui la concerne ; structure illisible ou campagne
   désignée → `conflict / retention_incoherent` (§ 9).
3. **Finalisation historique sans verrou de participation** : `finalize_idle_sessions` verrouille les visites sans
   la participation. Pas de cycle (elle ne demande rien après) ; son comportement est conservé (testé, y compris après
   l'échéance de conservation : limite L10).
4. **`cancelled` sans `closed_at`** : admis par les CHECK de 0022, refusé par l'échéance (`retention_incoherent`).
   Jamais remplacé par `now` ni `close_by_at`.
5. **Place de cohorte** : `cohort.attempt_first_login_admission` marque encore `admission_failure_first_at` d'une place
   sans participation lors d'une panne technique, y compris après la purge (caractérisé, L10).

## 6. Échéance de participation

```
planned    -> None (aucune échéance ; PR 4)
active     -> close_by_at + retention_days            (fin effective MAXIMALE)
closed     -> min(closed_at, close_by_at) + retention_days
cancelled  -> min(closed_at, close_by_at) + retention_days   (activée ou non)
```

Fin effective ramenée en UTC puis `timedelta(days=retention_days)` : arithmétique Python sur instants absolus
(90 jours = 2 160 heures). Validations préalables (sinon `RetentionDeadlineIncoherent`) : `common.validate_policy`
(`policy_incoherent`) ; statut du vocabulaire ; dates avec fuseau ; `created_at < close_by_at` ;
`created_at <= activated_at < close_by_at` ; `created_at <= closed_at <= close_by_at` et `activated_at <= closed_at` ;
planned sans activation ni clôture ; active activée et non clôturée ; terminal avec `closed_at` ; closed activée.
`retention_incoherent` sinon. 20 incohérences testées sans base ; l'égalité exacte rend la conservation échue
(`-1 µs` : conservée, ligne intacte `xmin` compris ; égalité : purge).

Testé sur PostgreSQL : campagne active avant / après `close_by_at`, clôturée normalement, prématurément, tardivement
(`closed_at = close_by_at`, aucune prolongation par le retard), annulée activée et jamais activée, planned avec inscrits
(jamais sélectionnée, `not_admissible / deadline_unestablished`), fuseaux de session UTC, Europe/Paris,
America/New_York, 90 jours franchissant les heures d'hiver (UE 25/10/2026, US 01/11/2026) et d'été (UE 28/03/2027,
US 14/03/2027) : 2 160 h absolues ; contre-épreuve `closed_at + interval '90 days'` différente sous Paris / New York.
